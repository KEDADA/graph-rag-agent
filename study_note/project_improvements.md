## 🛠️ 1. 架构代码与 Bug 修复 (Bug Fixes & Code Cleanup)

### 1-1. 空置的 `stream_llm` 实例（伪流式输出）
- **来源**：[Day 3 笔记](day3_note.md#22-初始化baseagent-启动时做了哪些准备) / QA-13
- **描述**：在 `BaseAgent` 初始化时，系统通过 `get_stream_llm_model()` 创建了一个支持流式输出的 LLM 实例 `self.stream_llm`。但在整个大图执行与生成的流程中，并未实际使用其 `astream()` 方法，而是通过截取普通 `.invoke()` 或整体返回再做前端拼凑来实现“伪流式”。
- **优化建议**：
  - **方案A**：如果项目决定不走真流式，应删除 `self.stream_llm` 的初始化和配置逻辑，清理死代码（Dead Code）。
  - **方案B**：重构 `generate` 节点，真正利用 AsyncGenerator 以流式往前端吐 token，降低首字响应时间（TTFT）。

### 1-2. `_generate_node` 中 `messages[-3]` 硬编码索引风险
- **来源**：[Day 3 答疑](day3_note_QA.md#qa-4为什么-_generate_node-通过-messages-3-获取问题这样写有问题吗)
- **描述**：在基础问答 Agent 的 `_generate_node` 中，为了获取用户的原始提问来给 LLM 提供上下文，源码直接使用了 `messages[-3].content` 的硬编码索引。这基于一个**极其脆弱的基假设**：`agent` 节点每次绝对只生成 1 个 `tool_call`（从而使得 `[Human, AI(1 tool), Tool]` 的长度固定为 3）。一旦遇到大模型并行并发多个工具调用，或者处理多轮对话的复杂 `messages` 追溯时，直接使用 `[-3]` 会立刻取错对象，导致生成回答的上下文错乱。
- **优化建议**：
  - 弃用固定的负数索引，改为逆向遍历 `messages` 列表，寻找到第一个类型为 `HumanMessage` 的实例。这不仅能完美规避上述结构破坏风险，还能兼容更复杂的 LangGraph 流转。

### 1-3. 全局缓存对“上下文追问”的错误命中（数据污染风险）
- **来源**：[Day 3 答疑](day3_note_QA.md#q12-3先查全局缓存不会导致那上海市奖学金呢返回错误答案吗)
- **描述**：当前 Agent 在生成回答后，会**无条件地将结果写入全局缓存**，且全局缓存的键仅为 `MD5(query)`。当用户在多轮对话中进行上下文紧密相关的追问（如：“那上海市的奖学金呢？”）时，该问题会被作为独立键存入全局缓存。后续如果其他用户在完全不同的上下文下碰巧问出同样的话（比如他在比对“上海市考公政策”），全局引擎会直接击穿缓存并返回前一个用户在奖学金语境下的答案，导致严重的回答错乱。
- **优化建议**：
  - **前置隔离**：在写入全局缓存前，增加意图/独立性判断逻辑（如调用微调小模型或正则判断是否含有指代补语）。对于“那xxx呢”这类强上下文依赖的追问，只写入带有 `thread_id` 隔离的**会话级缓存**，禁止污染全局缓存。
  - **融合上下文制键**：若确需全局缓存，则其 Key 值生成除了 `query` 外，必须加上代表用户当前意图的短期摘要（Context Summary）。

### 1-4. \`DualPathSearcher\` 架构设计与实际落地不符（名不副实）
- **来源**：[Day 4 笔记](day4_note.md#66-子模块3-dualpathsearcher双路径搜索器)
- **描述**：在 `DeepResearchTool` 深度研究的架构设计和命名中，`DualPathSearcher` 被设定为“双路径搜索”，其初始化时确实接收了 `kb_retriever` (本地知识库搜索) 和 `kg_retriever` (全局知识图谱社区搜索) 两个参数。**然而在代码实际落地的 `search(query)` 方法中**，所谓的两条路径其实变成了：路径1（剥离 KB名称的纯查询）和 路径2（强行带上 KB名称前缀的查询）。并且**这两条路径最终调用的全部都是 `kb_retriever` (Local Search)**，完全没有使用到传进来的 `kg_retriever`。这导致深度研究在收集证据时，实际上缺失了“宏观社区主题（Global Search）”这一维度的视角。
- **优化建议**：
  - **名副其实的重构**：修改 `DualPathSearcher.search()` 方法，让其中一条路径真正调用 `self.kg_retriever(query)` 并将返回的社区摘要 (Community Summary) 作为第二路证据源提供给 LLM 进行价值评估。
  - **修改架构文档**：如果作者是有意为之决定在深度研究中只使用 Local Search 进行细节深挖，则应彻底移除 `kg_retriever` 的传入参数，并将模块重命名为类似于 `AdaptiveQuerySearcher` (自适应词条搜索器)，避免后续维护者产生严重的架构误解。

### 1-5. 实体对齐阶段的“强制缝合”缺陷（缺乏分裂退出机制）
- **来源**：[Day 5 笔记](day5_note.md#25-合并实体call子查询隔离边处理) / 深度 QA 解析
- **描述**：在 `EntityAligner` 处理按 `canonical_id` 分组的实体时，一旦通过 Jaccard 计算发现存在关系冲突（即 `Jaccard < 0.5`），系统会调用 LLM 决定保留哪个实体作为最终壳子。然而，**当前代码设计缺乏“拒绝合并（Split）”的回退路径**。由于上一阶段的 WCC 聚类仅依赖粗颗粒度的向量相似度，极易将语义完全不同但字面相近的实体（如“国家奖学金”、“国家励志奖学金”）误分入同一组。尽管对齐阶段成功检测到了关系冲突，系统依然会无条件执行物理上的 `merge_entities`，将组内所有不相干实体的关系全部“赢者通吃”般强行缝合到唯一代表实体上，这就造成了不可逆的知识图谱污染（缝合怪现象）。
- **优化建议**：
  - **建立拒绝通道**：重构 `resolve_conflict` 的 LLM Prompt 及解析逻辑，让大模型首先判断组内实体“是否为同一事物”。如果 LLM 返回类似 `SPLIT` 的指令，则应跳过该组的物理合并流程，清除或重置这些实体的误打上的 `canonical_id` 标签，允许它们在图中保持原本独立的形态。

### 1-6. 冲突解决时 LLM 调用失败的“激进回退”策略
- **来源**：[Day 5 笔记](day5_note.md#25-合并实体call子查询隔离边处理) / 源码剖析
- **描述**：在包含了严重关联冲突的实体组中，当系统请求大模型裁决保留哪个代表实体时，如果因为网络错误、超时或响应格式不符导致 LLM 调用抛出异常，当前代码的回退策略是：`return max(entities, key=lambda x: x['rel_count'])['entity_id']`，即盲目选择关系数最多的实体，**并以此为基准强行合并废弃其他所有实体**。这一策略属于危险的“宁可错杀，不可放过”。既然 Jaccard 计算已发出冲突警报，说明这些实体大概率不能混为一谈；此时在失去 LLM 智能仲裁的兜底情况下暴力合并，会产生令人费解的节点聚合错误。
- **优化建议**：
  - **执行保守回退（Fail-Safe）**：将异常捕获块中的回退处理改为 `return None`（不代表任何实体）。并在外围的 `align_all` 中做兜底判断：一旦捕获到仲裁失败，系统应立刻中止当前分组的合并操作并抛出或打印 Warning 日志。对于含有冲突又不确定的数据，图谱构建的最佳实践应当是保持原始面貌（不合并），避免错误污染整个社区。

## 🚀 2. 性能与效率优化 (Performance & Efficiency Optimizations)

### 2-1. `history_aware_retriever` 无条件消耗 API
- **来源**：[Day 4 答疑](day4_note_QA.md#q3history_aware_retriever-是每次都会调用大模型吗如果我的新问题已经描述得很详细了它还会消耗一次-api-调用吗)
- **描述**：`LocalSearchTool` 中的上下文检索器在 `chat_history` 非空的情况下，无论用户当轮提问是否已经主谓宾完整（不需要重写），都会无条件地将历史记录和新问题抛给 LLM 进行改写判断。这白白增加了一次 LLM API 调用开销和网络延迟。
- **优化建议**：
  - 增加**意图识别前置路由**。在喂给 `history_aware_retriever` 前，通过轻量级 NLP 规则（正则指代词检测）或极小参数本地模型判断问题是否包含“他/这/那”等指代缺失，从而动态决定是否跳过改写阶段。

### 2-2. Session Level 缓存命中率过低（严格的 MD5 策略）
- **来源**：[Day 3 答疑](day3_note_QA.md#qa-12缓存机制怎么实现的为什么分两层)
- **描述**：会话级缓存（Session Cache）的键值生成逻辑使用 `MD5(query)`，即对用户输入字符串进行绝对哈希匹配。这意味着多出一个空格或一个语气词（如“请问旷课会退学吗” vs “旷课会退学吗？”）都会导致 Cache Miss，触发完整的检索和 LLM 生成。
- **优化建议**：
  - **向量语义缓存（Semantic Cache）降级**：可参考其 Global Cache 策略，对问题使用轻量级 Embedding 模型（如 SentenceTransformer），当向量相似度 > 0.95 时即认为命中会话缓存，大幅提高命中率。
  - **文本归一化预处理**：在求 MD5 之前，先剔除停用词、标点符号并做大小写与空格归一化。

## 💡 3. 新增功能与体验增强 (Features & DX)

### 3-1. 知识图谱构建依赖链过重 (`textract`)
- **来源**：Day 2 环境配置
- **描述**：项目在提取文档知识图谱时依赖了底层的 `textract` 库，而其在部分 Linux/WSL 系统上需要极为繁琐的系统底层级依赖（如 libxml2、poppler 等）。这给项目复现和跨平台部署带来了很大的环境污染问题。
- **优化建议**：
  - 更换轻量级或主流的 Python 文档解析器接口，如使用 `PyMuPDF`、`pdfplumber` 或者直接对接 Unstructured API 服务，降低部署门槛。
